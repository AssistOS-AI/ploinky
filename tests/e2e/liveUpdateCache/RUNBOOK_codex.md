# Live update and cache acceptance runbook

This records how the local acceptance harness is used, what it depends on, which failures it reports and how little it recovers on its own. It authorizes no execution. Every live statement below is "implemented and covered by fabricated controls" unless a run on the selected Ubuntu host says otherwise; the harness's own unit controls use fabricated engines, children and filesystems and never touch a Box, engine, network or credential.

## Entrypoint

```sh
npm test -- --acceptance /absolute/evidence/manifest_codex.json
```

`tests/run-all.sh` and `tests/test_all.sh` forward this test-only form and dispatch it to `tests/e2e/liveUpdateCache/run_codex.mjs` before any branch configuration, worktree, temporary workspace or AgentLib setup. Any other argument is refused (exit 64). The default `npm test` result stays component-only and says that live update/cache and release acceptance are UNRUN.

Exit codes: 0 = UC stage U0-U9 complete. Overall UC acceptance remains OPEN until AC-L4 G-BASE passes. 1 for a failed stage, 3 for `AWAITING_RELEASE_FIXTURE`, `AWAITING_SECOND_RELEASE_FIXTURE` or `RELEASE_IMAGE_WINDOW_INSUFFICIENT`, 64 for a refusal before any adapter exists. On exit 0 the receipt carries `acceptance: UC_STAGE_PASS`, `ucOverallAcceptance: OPEN` and `pendingRequirements: [AC-L4-G-BASE]` (fixed literals) and the last output line reads "UC stage complete; overall UC acceptance OPEN (pending AC-L4 G-BASE)". The runner never writes a plain PASS and has no code path that closes overall UC acceptance: that is recorded outside the runner, by the lead, only after an AC-L4 G-BASE PASS whose bindings match (same M4 or M6 scope, one physical execution, all bindings equal). A U0-U9 receipt, or this exit code, is never full UC acceptance. M4 and M6 acceptance stay pending until the live UC stage completes and AC-L4 G-BASE passes.

## Operator preparation (nothing below is created by the harness)

1. A manifest in the strict schema of `manifest_codex.mjs`, bound to the real pushed candidate. The harness defines these derivations and the manifest generator must use them: `engineIdentityOf` (engine identity from `podman info` version, graph/run roots, rootless, uid and path), `gpuWiringIdentityOf` (the Box GPU-grant label, or the fixed absent value), `publicationsId` and `mountsId` for the observed publications and read-only source mounts, and `selector.generation` (copied verbatim from the in-Box probe) for `box.activeGeneration`. `box.name` is the exact container name from the same exact-ID `container inspect` that binds `box.id` (leading `/` stripped; pattern `^ploinky-box-[a-z0-9][a-z0-9-]{0,200}$`, never the 64-hex ID), and `box.imageRef` is that Box's `io.assistos.ploinky-box.image-ref` label. Every live observation refuses (`live-box-contract`) a changed name or a present gpu-grant label that is not 64 lowercase hex characters.
2. An evidence root outside the workspace, candidate and participating repositories, mode 0700, containing no earlier receipt.
3. The source catalog `sources_codex.json` for the exact pushed candidate, built in a fresh process:
   `node tests/e2e/liveUpdateCache/catalog_builder_codex.mjs --candidate <root> --commit <40-hex> --out <evidence>/sources_codex.json [--extra <relative module>]`.
   It records Node's own resolve/load for one finite import of `ploinky-box/bin/ploinky-box.mjs` and `ploinky-box/supervisor.mjs`. Any import reached only at run time is absent and is refused by the worker; add it with `--extra` and rebuild.
4. `inputs_codex.json` in the evidence root: `schemaVersion`, `runId`, a digest-pinned `probeAgentImage` that already exists in the Box's nested image store, the absolute `releaseManifest` path of the Copilot gate (outside protected trees) and the exact `expectedUpdates` (errors, blockedBy, recordIds) for `normal-update` and `settling-update`.
5. Two fresh pinned release manifests, each created after the previous phase under its own grant by `release_manifest_writer_codex.mjs` (read-only; it records the Box ID, its container name and image reference from the same exact-ID inspect): `release_codex.json` (R1, `activation: null`) after U7b, and `release2_codex.json` (R2, `activation` declaring the three optional runtimes the activation adds) after the Copilot gate. Every generation is a fresh literal `ploinky start explorer` on the fixed canonical workspace path, recreated, over the identical candidate and image.

## Three-invocation flow

Invocation 1 runs U0-U7b. Cleanup completes, then B1 (the image age plus 6,150,000 ms must stay within four hours) is checked, and the receipts and settled-epoch record are frozen into `functional_codex.json`. With no `release_codex.json` yet it reports `AWAITING_RELEASE_FIXTURE` (exit 3), recording B1 as accepted, and creates no final receipt; a B1 refusal reports `RELEASE_IMAGE_WINDOW_INSUFFICIENT` (exit 3), freezes nothing and launches nothing release-side. Invocation 2, after the operator has recreated the fixture as R1 and written `release_codex.json`, verifies the frozen file (run ID, order, hashes, no gate credit), runs U7c and U8a (B2 first), creates `release1_codex.json` exclusively and reports `AWAITING_SECOND_RELEASE_FIXTURE` (exit 3). A repeat of invocation 2, or an invocation 3 before `release2_codex.json` exists, is refused (`release2-fixture-absent`) before any adapter exists; a tampered or orphaned `release1_codex.json` is `release-epoch1-invalid`. Invocation 3, after the operator has recreated the fixture as R2 and written `release2_codex.json`, verifies both frozen files and runs U7d, UA (B3 at its guard), U8b and U9. The operator's waits are not counted against the schedule. The entrypoint only requires the manifest's grant to be open; the run itself admits the whole schedule from U0 on a fresh start, the U7c-U9 suffix (5,880,000 ms) on invocation 2 and only the U7d-U9 suffix (3,480,000 ms) on invocation 3, against the grant window and the release manifest's own grant.

## Epoch stability across the canonical gates

Each gate's before and after observation records the active edge generation and every required runtime's identity tuple (name, runtime ID, instance ID, enable generation), and both are written into the gate evidence and the final receipt. Nothing may move between gates, and Copilot and WebMeet must leave the epoch exactly as they found it. Two windows exist. The UA window: the edge generation may change and exactly the three declared optional runtimes may appear, every default runtime unchanged (`activation-epoch-changed` otherwise); the state afterwards is observed twice and must be stable. The OnlyOffice window: the gate runs `ploinky restart onlyOffice`, so the edge generation and the row or rows of the `onlyOffice` agent may change, every other runtime must be unchanged, and the state after the window is observed again and must be stable before WebMeet starts from it. Each gate is bound to the epoch of its own generation (`canonical-gate-stale` otherwise).

## Operational constraint: outer Box age at the canonical gates

Before each gate the harness admits the remaining validity of the outer Box against the 30-minute generation clamp and the four-hour image limit, counting the work still to run inside the gate's own generation: Copilot on R1 570,000 ms (540,000 plus the 30,000 ms settlement allowance), OnlyOffice on R2 1,020,000 ms (840,000 plus 120,000 plus two allowances) and WebMeet on R2 150,000 ms. The Box's StartedAt therefore cannot be more than 1,230,000 ms old when Copilot begins on R1, 780,000 ms when OnlyOffice begins on R2 and 1,650,000 ms when WebMeet begins; an older Box refuses with `box-freshness-insufficient` and must be recreated. The activation is guarded too: the pre-guard admits UA only at a Box age of at most 150,000 ms (with the 30,000 ms install) and the activation guard at most 180,000 ms, otherwise `activation-window-insufficient`; an activation over its 540,000 ms guard fails closed at the OnlyOffice admission. B1, B2 and B3 add campaign-wide image reserves (6,150,000, 4,200,000 and 1,620,000 ms; `campaign-image-window-insufficient`). Re-reading metadata or restarting a nested agent never renews StartedAt. The 244-minute schedule does not widen either limit.

## Recovery limits

Private, append-only recovery records `recovery_<NNN>_<label>_codex.json` are written exclusively into the evidence root: the owned server's exact container ID and labels, the fixture directory and marker inodes (never the marker's content), the repository key and URL and the alias names, the registration intent before the commands that could half-succeed, and, on failure, the failed stage, reason, passed stages, unsettled commands and elapsed time. The server is launched with `--cidfile <evidence>/fixture/server.cid`, so its exact ID is recoverable even if the launch command fails. These records, not guesses, name what to remove by hand.

The first refusal stops the run and nothing is cleaned up by guesswork. The failure receipt names the failed stage and lists any unsettled retained command. Owned resources that may remain: the fixture directory `<evidence>/fixture` and its private marker, the BusyBox server container (exact ID recorded in memory only, label `io.assistos.ploinky-test.owner=<runId>`), the repository key and `.ploinky/repos/UcProbe<suffix>`, the aliases `uc-<suffix>-a|b`, the marker `update-persistence-<runId stem>_codex.txt` in the workspace, and the continuation fixtures `UpdateE2E-<runId>` and `.update-e2e-<runId>` with a possible `active-scope-restore_codex.json`. Remove them only with the same ownership proofs the harness uses (marker, inode, exact ID and labels, exact key and URL). A timeout, signal, overflow or unknown writer leaves recovery to the operator; the harness never signals a child, never kills a process group and never retries an update.

## Update expectations and the continuation runner

The expected record set of `normal-update` and `settling-update` must name the run-owned repository record (`UcProbe<suffix>`) and, for `normal-update`, the Git-pin record of the owned registration, whose id is derived exactly as the product derives it (`owned_ids_codex.mjs`, compared in its control with the product's own container-name and pin-id functions). A real update also emits Git-pin records for every non-owned enabled registration that declares a Git dependency, and registered-repository or default-skills records for deployed repositories. Immediately before each update the harness therefore observes that vocabulary in the Box (`pin_probe_codex.mjs`: the product's own pin refresh, offline, over a read-only pin view, no lease, no write): the pin ids join the expected set, those ids, the enabled registration keys and the registered repository names are admitted for the update's validation, and the owned pin and registration must have been observed or U4 refuses. The operator file is only shape-checked at load; its errors, blockers and every other id still have to match the update's records exactly. If a registration's repository is not verified by the update, its pin records are replaced by a skipped record keyed by the registration, the observed set no longer matches and the update is refused rather than absorbed. Workspace-repository records (absolute paths of checkouts outside `.ploinky/repos`) cannot be observed this way and must be listed from an observed inventory. The continuation runner (U6) still judges its two updates from the outer CLI's output wording plus the product's own recovery state, not from the structured worker, because a structured proof needs the exact full record inventory of those updates, which only an observed run can supply. It clears its retain-fixtures guard only for a proven normal return (normal activation wording, no exception-path output, no recovery barrier, readable update state), and it admits against the generation the parent has itself admitted, passed with `--generation`.
