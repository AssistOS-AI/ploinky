Execution Model

Ploinky Documentation

The runtime layer is responsible for workspace discovery, repository-backed agent discovery, per-agent workspace state, execution-backend selection, and the wave-based startup sequence that feeds the router’s route table.

Workspace State

Path Purpose
.ploinky/agents.json Enabled-agent registry plus workspace configuration under the reserved _config key.
.ploinky/repos/ Cloned agent and skills repositories managed by install/add and uninstall/remove.
.data/<agent-or-alias>/ Persistent host-side agent home mounted at /root for enabled-agent instances. Destroy preserves this directory.
.ploinky/code/ and .ploinky/skills/ Symlink layer exposing each enabled agent’s source tree and optional skills folder.
.ploinky/deps/ Runtime-keyed global and per-agent Node dependency caches. Destroy clears this regenerated cache.
.ploinky/keys/ Router and agent Ed25519 key material for secure delegated calls.
.ploinky/logs/ Router, watchdog, and command logs used by status surfaces and debugging workflows.

Agent Enablement and Run Modes

enable agent resolves a manifest through repository discovery, enforces alias uniqueness, chooses an auth mode, and stores a normalized record in .ploinky/agents.json. If the static agent passed to start is not already enabled, the CLI enables it automatically before booting the workspace.

isolated

The default mode uses .data/<agent-or-alias>/ as both the per-instance working directory and the persistent home mounted at /root.

global and devel

global points the agent at the workspace root. devel points the agent at a repository checkout under .ploinky/repos/<repo>/. Both modes still mount .data/<agent-or-alias>/ at /root for CLI and tool configuration.

Aliases become route keys and container names. This is how Ploinky supports multiple instances of the same agent in one workspace without overwriting the registry entry for the canonical instance.

Runtime Backends and Mount Policy

Outside a marked Ploinky box, the container path is the default backend and auto-detects podman before docker. Agents with lite-sandbox: true run through the host sandbox backend when available: bwrap on Linux and seatbelt on macOS. Ploinky does not silently fall back from a requested host sandbox to containers; use ploinky sandbox disable when podman/docker testing is desired. Inside a contract-6 marked box, every managed agent, helper, sidecar, probe, and install-container path uses nested Podman; retained sandbox settings, Docker, bwrap, and Seatbelt are not fallbacks.

When stopping or destroying multiple host-sandboxed agents, Ploinky sends the graceful signal to all selected sandbox process groups before waiting. It then uses one shared deadline and force-kills only the sandbox processes that are still alive, so one stuck agent does not delay signal delivery to the rest of the workspace.

Profile handling is merged from manifest profiles.default plus the active profile from .ploinky/profile. In dev, code and skills mounts default to read-write. In qa and prod, they default to read-only unless the profile explicitly overrides them.

Outer Box contract 6 is a clean hard cut over core runtime v5. Every managed outer ploinky-box has exactly two engine publications: 127.0.0.1:<selected-router-host-port>:8080/tcp and 0.0.0.0:7882:7882/udp. The wrapper constructs both mappings directly; profiles, manifests, dependency graphs, readiness, labels, and persisted state cannot add a physical-host publication. Outer --port selects only the loopback host side of fixed inner Router port 8080; --publish, --expose, and --listen-lan are rejected. Older Box contracts are rejected and must be recreated explicitly by an operator.

A contract-6 box is reused or started only when its normalized creation configuration matches exactly. Port, image, mount, device, security, or other creation drift fails before pull, stop, rename, removal, or creation. The operator must run ploinky destroy explicitly before recreation; no automatic replacement, backup rename, or rollback path exists.

An agent may declare browser targets with the existing httpServices entries and optional httpServices[].port. An omitted port selects the primary target; each distinct explicit TCP port gets one private inner mapping. No secondary-target field or special proxy exists. Inner targets remain private to the box network and never become outer publications.

Managed bridge launches use exactly --hosts-file=none --add-host host.containers.internal:host-gateway. That mapping is fixed name/address transport configuration, not a capability and not authorization. By contrast, manifest network.mode: host requires a Ploinky-granted capability for one exact effective instance and current enable generation. Even that capability grants only network placement; localhost or source-address provenance never authorizes a request.

Every managed process is also bound physically to that tuple. Container labels persist the exact instanceId and enableGeneration; bwrap and Seatbelt use a schema-2 PID/start-identity record with the same fields. Reuse and capability checks compare those immutable launch records to the selected generation, and identity derivation failure aborts startup instead of launching without a private assertion secret.

Inside a marked Box, private Router port 8081 binds the Box namespace wildcard so nested rootless Podman can reach it through host-gateway. It is never an outer publication, and source-address reachability grants nothing: every private request still requires an exact generation-bound, replay-protected assertion that binds its caller, method, path, and body.

Sandboxed Job Delegation vs lite-sandbox

The Basic catalog bwrap-runner agent is a separate, optional mechanism from lite-sandbox: true. lite-sandbox: true selects a host sandbox backend (Linux bwrap or macOS Seatbelt) for the entire agent process. bwrap-runner is a normal containerized agent that exposes an MCP tool sandbox_exec, so other agents can delegate a single bounded command to a nested inner bubblewrap sandbox without changing how their own runtime is selected. v1 does not transparently replace host bwrap: getRuntimeForAgent() still dispatches lite-sandbox: true agents to host bwrap on Linux or Seatbelt on macOS.

Nested bubblewrap still depends on host and outer-OCI runtime policy. The runner image ships bwrap and runs a startup nested-bwrap smoke command, but it cannot bake host sysctls such as kernel.unprivileged_userns_clone into the image. If the outer container runtime blocks CLONE_NEWUSER, readiness fails with an actionable error and the operator must adjust host or runtime policy.

A required environment entry may omit default or value when no safe deployment-independent value exists. It then becomes an explicit operator/provider prerequisite: profile readiness and launch resolve encrypted vars, startup-provider output, process environment, and .env, and fail with the exact missing name. Ploinky never infers URLs, hostnames, public IPs, realms, ports, or Origins. Safe portable defaults and generated-secret behavior remain unchanged.

Manifest volumes resolve relative host paths against the workspace root and honor absolute host paths as declared. Runtime-resource persistent storage should prefer .ploinky/data/, while agent-owned home files and generated startup inputs should prefer .data/<agent-or-alias>/. Container destinations should use semantic paths such as /data, /root, or /working-data/generated unless an upstream image requires a specific path. Runtime resource planning can also create persistent storage directories under .ploinky/data/ and template environment values from workspace roots, storage paths, secrets, and variables.

Dependency Waves and Readiness Gating

Ploinky first prepares the recursive manifest repository graph without enabling processes. It then captures an early inactive targetless generation for every retained or newly assigned graph identity before the fatal static preinstall hook and startup config providers run. After providers finish, Ploinky aborts the early lease, reloads the registry, re-evaluates retained predecessor runtime hashes, rotates any newly stale tuple, and captures the final inactive targetless generation. Only that final lease may authorize targets. Runtime launch preserves its exact identities; each blocking wave records resolved private targets through coordinated apply and passes readiness before the next wave may boot. Additional already-enabled agents outside the graph start after the blocking waves. Detached no-wait helpers are spawned last; the main command does not wait for their cache preparation, runtime startup, or readiness after spawning them.

An explicit readiness.protocol of tcp, mcp, or none wins. Without an explicit protocol, a start-only service with health.readiness.script uses the blocking script probe; another start-only service needs a reachable private target for TCP readiness. Execution modes that include AgentServer default to an MCP handshake. none is only for a true worker with no serving readiness surface.

Semantic health continues after startup at a bounded recurring interval. A later socket-owner or service-semantic failure inactivates routing before an exact-identity replacement is attempted; one historical success is never permanent ownership evidence.

Static Agent Responsibilities

The static agent determines the default browser entry route in the validated immutable route-and-policy authorization generation. Requests for / and /index.html redirect to the static agent's routed /<agent>/index.html path. The router does not read the static agent's files from static.hostPath; it strips the /<agent> mount prefix and proxies the request to the agent server.

The agent server must serve its own index.html and related assets. The shared AgentServer serves static files from PLOINKY_CODE_DIR or /code after its built-in endpoints. Agents that use a custom manifest.agent command must implement the same static-file responsibility in that command.

Ploinky mounts the current box-owned, non-secret topology before a consumer starts. The snapshot distinguishes the route-and-policy authorization generation, a content-derived configuration generation, and a monotonic readiness/publication generation. Generic core records only declared service selectors and locator projections; it does not hardcode optional product identifiers. Browsers can obtain only one authenticated, no-store locator with configuration/publication ids, never the authorization id or inventory.
