Router Surfaces

Ploinky Documentation

The interface layer combines a supervised local router, prefixed browser surfaces, HTTP and MCP proxy routes, and authentication that can operate with dashboard tokens, guest sessions, or a configured SSO provider agent.

RoutingServer and Watchdog

cli/server/RoutingServer.js owns HTTP request dispatch. cli/server/Watchdog.js owns process supervision, health-check restarts, restart backoff, and container monitoring. The router exposes a health endpoint at /health, browser assets, blob upload and download endpoints, and both router-level and agent-level MCP routes.

The router uses the active route table from .ploinky/routing.json. Its protected paths are authenticated before dispatch, except where a route is explicitly defined as public or where agent-delegated MCP verification must inspect the request body before making an auth decision.

Browser Surfaces

Prefix Current Behavior
/webchat TTY-backed chat surface that persists encrypted transcripts, supports uploads, and forwards arbitrary URL query parameters to the selected agent CLI as long-form flags encoded as single --key=value tokens.
/dashboard Management surface with transcript and feedback access controls. The active fallback assets live under cli/server/dashboard/.
/status Read-only status UI that shells out to ploinky status, adds router-side server and workspace-agent summaries, and accepts a dashboard invitation link or WEBDASHBOARD_TOKEN for token access.

The root-level dashboard/ directory is not the active fallback for routed /dashboard. The current implementation resolves fallback dashboard assets from cli/server/dashboard/, which is why the product documentation follows that path.

For /webchat, the router treats agent as the agent selector and preserves any other query parameters on the browser session URL. When an explicit agent is selected, those additional query parameters are forwarded to ploinky cli <agent> as long-form CLI arguments encoded as single --key=value tokens using the same values carried in the URL.

Authentication Modes

Ploinky supports three practical access patterns. /webchat uses the normal router login flow. /dashboard still supports WEBDASHBOARD_TOKEN, and the read-only /status surface reuses the dashboard token flow. SSO stores a configured provider agent in workspace SSO config; provider agents mark their manifests with "ssoProvider": true. Guest-capable routes use scoped router-issued guest sessions.

The auth bridge normalizes authenticated users onto req.user and tracks session cookies for SSO and guest sign-in paths. SSO sessions inherit user identity and tokens from the provider flow.

Marketplace API

The router owns a JSON Marketplace API for first-party agent and repository management. GET /api/marketplace returns the current caller, marketplace permissions, installed and default repositories, remembered repository sources, repository kind, discoverable agents, enabled-agent records, and each agent's live runtime status when a matching Ploinky container is running. The read endpoint requires an authenticated SSO user, and non-admin clients use the returned permissions to hide management controls.

POST /api/marketplace accepts repository actions named install_repo and uninstall_repo, plus agent actions named enable_agent and disable_agent. Repository installation clones the checkout and records source metadata. Repository uninstall disables enabled agents from that repository, removes their runtime containers, removes the checkout, and preserves source metadata for reinstall. Agent enablement uses the standard enable path. Agent disablement is intentionally specific to this admin API: the route removes the enabled-agent registry record before removing the runtime container so the watchdog container monitor does not restart the agent during the operation.

Marketplace mutations require an authenticated admin user from the SSO session. The route is router-owned management API, not an agent proxy route, not a manifest HTTP service, and not an HTTP route-access policy entry.

Agent Cards and Secure Delegation

Ploinky reads installed manifests into a small agent index for route names, principals, runtime resources, and SSO-provider markers. Provider-specific domain authorization lives in the target agent.

The router exposes agent-card discovery at /agent-card and /<agent>/agent-card. The aggregate endpoint queries each active route's agent-side /agent-card endpoint and returns successful responses without requiring a fixed metadata schema; per-agent failures are reported separately. Agent metadata can include tags, summaries, input conventions, schemas, or any other JSON fields useful to an orchestration layer.

OpenAI-compatible agent calls are routed through /<agent>/v1/chat/completions. The request body controls response mode: stream: true preserves the agent's SSE stream, while an absent or false stream flag returns the normal JSON completion response.

/agent-card and /<agent>/v1/chat/completions are public at the router level; the target agent decides whether to accept or reject the request. Orchestrators discover remote agents through PloinkyAgentSkillsSubsystem and declare them via ## Allowed Agents in oskill.md.

For delegated MCP and protected service calls, the router mints short-lived Router Request JWTs signed with the target agent's own PLOINKY_AGENT_SECRET. Agents and services verify audience, method, path, optional tool, request-content hash, expiry, and replay id before trusting forwarded identity.

MCP and HTTP Service Paths

The router aggregates tools and resources at /mcp, while agent-specific MCP endpoints are exposed under /<agent>/mcp. Agent task-status passthrough lives at /<agent>/task. Public and authenticated HTTP service routes are defined separately and may inject compact auth headers for downstream agents; protected service invocation tokens bind the forwarded method, rewritten service path, query string, and body hash.

This split lets Ploinky expose first-party routing behavior and agent-specific protocol proxies without forcing every browser surface through the same transport semantics.
