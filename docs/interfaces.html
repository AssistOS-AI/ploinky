Router Surfaces

Ploinky Documentation

The interface layer combines a supervised local router, prefixed browser surfaces, HTTP and MCP proxy routes, and authenticated sessions backed by local credentials or a configured SSO provider agent.

RoutingServer and Watchdog

cli/server/RoutingServer.js owns a public/control listener on fixed inner port 8080, mapped only to the physical host's selected loopback port, and an un-published box-private listener on 8081. Detailed supervisor health is available only through an unmounted Unix socket. Every TCP admin, control, and status handler requires a real local-admin session, and mutations additionally require valid Origin and CSRF checks.

Inside a marked Box, private 8081 binds the Box namespace wildcard so nested rootless Podman can reach it through host.containers.internal:host-gateway. The outer runtime never publishes that port, and transport reachability grants no authority: route policy, caller ACL, and an exact generation-bound private assertion remain mandatory.

HTTP, SSE, and WebSocket traffic share one resolver and one validated immutable route-and-policy authorization generation. Listener class and exact Host are resolved before pathname dispatch; dedicated service hosts and agent-root hosts have closed route-surface allowlists. Unknown, malformed, stale, suffix-confusable, and unauthorized host/path combinations fail before any upstream dial.

A host selects a declared httpServices service, canonicalized to its externalPrefix. The provider and the effective HttpRouteAccessPolicy independently admit the request. Candidate file edits have no effect until coordinated apply digests and validates the exact bytes, deactivates affected selectors, and atomically activates a new generation.

Browser Surfaces

Prefix Current Behavior
/webchat TTY-backed chat surface with agent-owned session snapshots, lazy history rendering, uploads, and generic selected-agent CLI argument forwarding.
/dashboard Operational management surface for status, logs, agents, and runtime control. The active fallback assets live under cli/server/dashboard/.
/status Read-only local-control status UI that shells out to ploinky status, adds router-side server and workspace-agent summaries, and requires a real authenticated local-admin session.

The root-level dashboard/ directory is not the active fallback for routed /dashboard. The current implementation resolves fallback dashboard assets from cli/server/dashboard/, which is why the product documentation follows that path.

For /webchat, the router treats agent as the agent selector and preserves ordinary query parameters on the browser session URL. When an explicit agent is selected, those parameters are forwarded to ploinky cli <agent> as single-token --key=value arguments. Router-owned tabId values are not forwarded.

Conversation sessions have no WebChat REST API. A compatible CLI publishes current, list, and selected records through __webchatSession; the router validates them and emits session-state events. The browser requests changes with /session, /session new, or /session resume <session-id>.

Generic CLI interactions use named interaction-request and interaction-resolved events on the existing WebChat EventSource. The browser answers through authenticated POST /webchat/interaction; the route validates the active subscriber, tab, runtime, request id, and declared option before delivering control input to the CLI TTY.

Authentication Modes

/webchat uses the normal router login flow. /dashboard and /status require a real router-authenticated local-admin session on an exact local-control Host; component tokens, invitations, assertions, media credentials, and localhost provenance do not satisfy that requirement. Control mutations additionally require the exact Origin and a session-bound CSRF proof. Local auth stores hashed users inside a workspace-managed variable such as PLOINKY_AUTH_<ROUTE>_USERS. SSO stores a configured provider agent in workspace SSO config; provider agents mark their manifests with "ssoProvider": true.

The auth bridge normalizes authenticated users onto req.user and tracks session cookies for both local and external sign-in paths. Local sessions are handled by the router’s session store, and SSO sessions inherit user identity and tokens from the provider flow.

Marketplace API

The router owns a JSON Marketplace API for first-party agent and repository management. GET /api/marketplace returns the current caller, marketplace permissions, installed and default repositories, remembered repository sources, repository kind, discoverable agents, enabled-agent records, the recorded runtime backend, and each agent's live state. Runtime detection follows the enabled record: Bubblewrap and Seatbelt use their tracked process PIDs, while Docker and Podman use OCI inspection. Browser reads require an authenticated local or SSO user, and non-admin clients use the returned permissions to hide management controls. A running Ploinky agent may read the same state with a request-bound Agent Assertion for marketplace.read.

POST /api/marketplace accepts repository actions named install_repo and uninstall_repo, plus agent actions named enable_agent and disable_agent. Repository installation clones the checkout and records source metadata. Repository uninstall disables enabled agents from that repository, removes their runtime containers, removes the checkout, and preserves source metadata for reinstall. Agent enablement uses the standard enable path. Agent disablement is intentionally specific to this admin API: the route removes the enabled-agent registry record before removing the runtime container so the watchdog container monitor does not restart the agent during the operation.

Browser mutations require an authenticated local admin user. Agent callers have one narrow exception: a request-bound, replay-protected assertion for marketplace.enable_agent may submit only enable_agent, allowing an active agent to start an installed dependency on demand. Agents cannot install or uninstall repositories, disable agents, or inherit browser administrator permissions. The route is router-owned management API, not an agent proxy route, not a manifest HTTP service, and not an HTTP route-access policy entry.

Agent Cards and Secure Delegation

Ploinky reads installed manifests into a small agent index for route names, principals, runtime resources, and SSO-provider markers. Provider-specific domain authorization lives in the target agent.

The router exposes agent-card discovery at /agent-card and /<agent>/agent-card. The aggregate endpoint queries each active route's agent-side /agent-card endpoint and returns successful responses without requiring a fixed metadata schema; per-agent failures are reported separately. Agent metadata can include tags, summaries, input conventions, schemas, or any other JSON fields useful to an orchestration layer.

OpenAI-compatible agent calls are routed through /<agent>/v1/chat/completions. The request body controls response mode: stream: true preserves the agent's SSE stream, while an absent or false stream flag returns the normal JSON completion response.

/agent-card and /<agent>/v1/chat/completions are public at the router level; the target agent decides whether to accept or reject the request. Orchestrators discover remote agents through PloinkyAgentSkillsSubsystem and declare them via ## Allowed Agents in oskill.md.

For delegated MCP and protected service calls, the router mints short-lived Router Request JWTs signed with the target agent's own PLOINKY_AGENT_SECRET. Agents and services verify audience, method, path, optional tool, request-content hash, expiry, and replay id before trusting forwarded identity.

Box-private service calls additionally require authenticated policy admission and an exact caller ACL for the current instance and enable generation. The short-lived assertion uses a separately derived tuple secret and binds its type, audience, caller, generation, method, canonical path, query, body digest, and replay state. It is a capability for one service call, not a user or administrator credential, and the captured authorization generation is revalidated immediately before every HTTP, SSE, or WebSocket upstream connection.

Mounted topology distinguishes the immutable route-and-policy authorization generation, a content-derived configuration generation, and a monotonic readiness/publication generation. The authenticated no-store browser projection returns only one active locator plus configuration/publication ids; it exposes neither the authorization id nor topology inventory.

MCP and HTTP Service Paths

The router aggregates tools and resources at /mcp, while agent-specific MCP endpoints are exposed under /<agent>/mcp. A public agent-root host that selects the agent-mcp capability compiles an exact allowlist from the selected root and its transitive active-manifest dependency closure; unrelated enabled routes cannot become MCP targets, and non-MCP dependency-looking paths remain selected-root content. Agent task-status passthrough lives at /<agent>/task. Public and authenticated HTTP service routes are defined separately and may inject compact auth headers for downstream agents; protected service invocation tokens bind the forwarded method, rewritten service path, query string, and body hash.

This split lets Ploinky expose first-party routing behavior and agent-specific protocol proxies without forcing every browser surface through the same transport semantics.
