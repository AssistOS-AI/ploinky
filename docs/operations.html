Operator Workflow

Ploinky Documentation

Operations in Ploinky center on secret resolution, dependency-cache hygiene, observability, test execution, and the maintenance tooling that keeps browser docs, specs, and command-suggestion context aligned with the code.

Secrets and Variable Resolution

Workspace-managed secrets live in .ploinky/.secrets. The secret injector also walks upward to find the nearest .env file and prefers process environment variables over both file-based sources. This precedence model is shared by auth config, runtime resource templating, dependency tooling, and the LLM helper. Manifest entries marked generatedSecret: true are intentionally different: Ploinky derives them from the agent identity and ignores same-named operator variables.

var, vars, echo, and expose are the operator-facing commands for that layer. Variable exposure supports wildcard expansion, but the all-match * pattern deliberately excludes names containing API_KEY so sensitive values are never exposed accidentally through a broad manifest pattern.

Branch-Aware Startup

ploinky start accepts --branch <branch> to set a candidate branch for managed repos involved in startup, --repo-branch <repo=branch> to override the candidate per repo, --branch-fallback default|fail to control missing-branch behavior, and --reset-repos to permit hard reset of dirty checkouts. Bootstrap applies the global branch only to the prefixed static-agent repo and applies explicit per-repo overrides to default boot repos. Manifest repos values may be objects with an explicit branch field, and prefixed enable entries use the normal source lookup both to install missing repos and to reconcile already-installed dependencies with the active branch policy. Branch metadata is recorded in .ploinky/repo_sources.json for reproducible restarts.

The local router uses the printed 127.0.0.1 URL as its canonical public authority. A GET or HEAD request to the same port through the exact localhost loopback alias receives a non-cacheable redirect to that canonical address; unsafe methods and other unknown or malformed Host authorities still fail closed.

An enabled agent outside the resolved static dependency graph may declare startup: "manual" to remain dormant during general start and restart operations. Missing startup means automatic. Static agents and explicit manifest dependencies always start, even if their own manifest says manual. A running manual agent is retained; a stopped one has its stale route removed until an explicit Marketplace or CLI activation recreates it.

Dependency Cache Maintenance

ploinky deps prepare, deps status, and deps clean manage runtime-keyed Node caches under .ploinky/deps/. Global caches are prepared from globalDeps/package.json. Per-agent caches merge that baseline with an agent-local package.json when one exists. A cache is valid only when the runtime key, merged-package hash, stamp version, installer metadata, and core marker module all match the current inputs. ploinky start prepares or refreshes missing and stale caches before launching agents, so first startup may require npm, git, network access, and native build tools.

Container runtimes prepare caches inside a short-lived install container for the target image and record that image in the cache stamp so manifest image changes refresh stale native dependencies. Sandbox runtimes prepare caches on the host, but only when the runtime key matches the host runtime family and platform.

Observability

The watchdog and router write structured logs under .ploinky/logs/. The CLI currently exposes only router log tailing and last-line inspection through logs tail and logs last. The status surface also shells out to ploinky status, then adds router-side server and enabled-agent summaries so operators can compare the CLI view with the browser view.

WebChat conversation continuation is project state under <cwd>/.copilot_history/, not an operational log. The browser lists folder sessions without message bodies and loads the selected history only when the user requests it.

Routing and Socket-Boundary Checks

Routing activation is content-addressed and fail-closed. A candidate must contain complete agent, enable-generation, effective-instance, container, relay, listener, limits, denied-port, policy, and private-ACL inputs. Editing staging files does not change an in-flight request; a successfully compiled replacement atomically activates and invalidates uncommitted leases.

The expected network boundary is one operator-selected public RoutingServer TCP listener. Agent application ports and the exec/stdio relay are not host-published. The private machine-call listener is exactly 127.0.0.1:8081 and remains disabled when a container-side proof cannot reach that loopback binding through the runtime-owned host alias. Media UDP provisioning, when present in a deployment fixture, remains a separate direct plane.

Run npm run e2e:routing-proxy to exercise the real container relay, private exposure, capacity/failure, network-boundary, and Playwright base-path gates. Run the same command with -- --livekit only with PLOINKY_LIVEKIT_E2E_COMMAND configured for a real deployment; the command must emit final JSON evidence for routed signaling, no browser private dial, a remote screen-share track, increased media bytes, and private assertion-plus-ACL enforcement.

Access Tokens and Invitations

webchat prints the router login URL for the chat surface. Only dashboard mints or reuses a workspace token through WEBDASHBOARD_TOKEN.

The read-only /status surface does not have a separate token namespace; it accepts a dashboard invitation link or the dashboard token instead.

Skills and LLM Assistance

default-skills refreshes every skill directory from a skills repository under .agents/skills/. Re-running the command replaces only skill folders owned by that source repository, so files removed upstream do not linger locally while unrelated existing skills are preserved. A workspace ploinky-skills-manifest.json uses an array of objects with url, name, optional branch, and selected skills; update clones or pulls those repositories in .ploinky/repos and reconstructs .agents/skills strictly from that selection. Legacy skills found under .claude/skills/ are migrated into .agents/skills/ before Claude compatibility symlinks are created, and the managed .gitignore block lists only the refreshed source skill folders plus the .claude compatibility path.

update also refreshes Achilles default skills for project repositories discovered from the update search root. Before project discovery, the Ploinky runtime node_modules/achillesAgentLib checkout is refreshed, and installed repositories under .ploinky/repos/ are pulled, or recloned on their recorded branch when a directory is missing direct git metadata but Ploinky knows the source URL. The update, update all, update repos, and update repo <name> flows refresh AchillesCopilotBasicSkills into eligible installed .ploinky/repos/ entries through the same default-skills behavior, skipping the AchillesCopilotBasicSkills source repo and skills-only repos. Discovered project repositories with missing or unreachable remotes are logged and skipped for the pull step, while default skills are still refreshed in them. Without an explicit folder path, that search starts at the current working directory; with a folder path, discovery starts there and includes the root when it is itself a git repository.

ploinky-shell and invalid-command fallback logic rely on Achilles LLM tooling. The suggestion prompt reads docs/ploinky-overview.md, inspects configured API-key sources, and uses the current model settings from workspace variables such as ACHILLES_MODEL_PLAN. If CLI behavior changes and that overview file is not updated, the suggestion layer becomes stale even when the main docs are correct.

Testing and Documentation Verification

tests/test_all.sh is the full-stage regression harness. It can optionally test another branch by creating a git worktree when PLOINKY_BRANCH is set. tests/runFailingFast.sh rebuilds one fresh workspace and reruns only the previously failing checks to shorten iteration time after a broken run.

Documentation verification is part of the repository contract. After documentation changes, regenerate docs/specs/matrix.md, copy docs/specsLoader.html from the GAMP asset, verify local links, and run the static-site verifier against the finished docs/ directory.

Use fileSizesCheck.sh when documentation or generated content grows substantially. The canonical script lives at the repository root and is referenced from the coding-style specification.
